# Azure Policy Definition and Assignment

Creates one custom Azure Policy definition and can optionally assign it at management group, subscription, or resource group scope.

## Features

- Custom policy rule, parameter schema, metadata, mode, display name, and description
- Optional management group-scoped policy definition
- Optional assignment at one supported governance scope
- Assignment exclusions, metadata, parameters, non-compliance messages, and enforcement control
- Optional system-assigned identity and operation timeouts
- Deterministic generated naming when `name` is omitted

## Resources Created

The module always creates one `azurerm_policy_definition`. When `create_assignment` is enabled, it creates exactly one scope-specific policy assignment resource.

It does not create policy initiatives, exemptions, remediations, or the role assignments required by `deployIfNotExists` and `modify` policies.

## Prerequisites and Dependencies

- Azure permissions to create a policy definition at the selected definition scope
- Permission to create an assignment at `assignment_scope`
- An existing management group, subscription, or resource group for an assignment
- An Azure region when the assignment uses a system-assigned identity
- Separate RBAC ownership for any identity used by policy remediation

Create the management group hierarchy before management group definitions or assignments. Review policy effects and exclusions as production governance changes.

## Basic Usage

```hcl
module "require_owner_tag" {
  source = "./modules/policy"

  name         = "require-owner-tag"
  display_name = "Require Owner tag"
  policy_rule = jsonencode({
    if = {
      field  = "tags['Owner']"
      exists = "false"
    }
    then = {
      effect = "audit"
    }
  })

  metadata = jsonencode({
    category = "Tags"
  })
}
```

See [examples/basic](./examples/basic), [examples/complete](./examples/complete), and [examples/management-group-assignment](./examples/management-group-assignment).

## Scope and Lifecycle

`management_group_id` controls where the definition is stored. `assignment_scope` independently controls where the optional assignment applies. The assignment scope must be an exact management group, subscription, or resource group resource ID.

Use one module instance per definition. When definition and assignment lifecycles have different owners or release cadences, create only the definition here and manage assignments in a separate stack.

## Identity and Remediation

The optional assignment identity is system-assigned. Creating that identity does not grant it permissions. Policies using `deployIfNotExists` or `modify` normally require role assignments at an appropriate scope before remediation can succeed.

## Testing

The tests use a mocked AzureRM provider and plan-only runs:

```powershell
terraform init -backend=false
terraform test -filter=tests/unit.tftest.hcl
```

No Azure policy resources or tenant changes are made by the test suite.

## Known Limitations

- One custom policy definition is created per module instance.
- Only management group, subscription, and resource group assignments are supported.
- Only `SystemAssigned` assignment identity is supported.
- Policy JSON is syntactically validated, but Azure policy aliases, effects, parameters, and permissions are validated by Azure at apply time.
- Initiatives, exemptions, remediation tasks, and remediation RBAC are outside the module.

See [Architecture](./docs/architecture.md) for scope ownership and deployment sequencing.
